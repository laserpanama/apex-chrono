# Apex Chrono V1 — GNSS lap timing implementation

V1 answers one question: how fast was the lap? This document covers the GNSS timing layer that answers it: what the code does, how it was validated, and what is left before a real track day.

Measured results are in [`docs/V1_VALIDATION_REPORT.md`](docs/V1_VALIDATION_REPORT.md), generated by `npm run validate:gps`. The tables below are copied from that run.

## 1. Architecture

```
            ┌──────────── browser preview ────────────┐      ┌──────── ESP32-S3 firmware ────────┐
 truth      │ SessionEngine (speed profile, pose)     │      │ BN-880 UART → TinyGPSPlus (NMEA)  │
 source     │   └─ gnssFix(): noisy 10 Hz fix         │      │   └─ apex::GnssFix                │
            └───────────────┬─────────────────────────┘      └───────────────┬───────────────────┘
                            ▼                                                ▼
            src/lib/gnss (TypeScript reference)  ══ parity-tested ══  firmware/lib/apex_timing (C++17)
              fix.ts        quality filter (sats, HDOP, fix type, monotonic GNSS time)
              geo.ts        WGS84 lat/lon → local east/north metres
              centerline.ts closed-loop centerline, map matcher (s, cross-track)
              gates.ts      geographic gate detector (state machine + refined crossing time)
              lap-engine.ts sector/lap state machine → GpsLapRecord, best lap, deltas
                            ▼                                                ▼
            Zustand store snapshot → React cockpit           serial event log (display + SD next)
```

All of `src/lib/gnss` is plain TypeScript with no DOM, server or package dependencies. The same code runs in the browser, in `node --test`, and in the validation harness. `firmware/lib/apex_timing/apex_timing.h` is a line-for-line C++ port of it with no heap. A host test replays fixtures exported from the TypeScript engine and requires identical laps.

### The supplied package (`apex-chrono-v1-final.zip`)

I reviewed every file in the package. Its pipeline (`gps.ts`, `gates.ts`, `gps-lap-engine.ts`) is the same in concept, and its own report shows the problems this implementation fixes:

- It intersects the segment between two consecutive noisy fixes with the gate line. It missed 5, 76 and 353 of 999 laps at 3, 5 and 10 m.
- It stamps laps at fix time instead of the interpolated crossing time.
- It uses spherical constants (110540 / 111320·cosφ).
- Its lap engine does not check sector order against the S/F line.

I kept its ideas and contracts: the separate cockpit simulator, the gate direction, speed, HDOP, sats and cooldown guards, the `BN-880 UART → parser → engine → display/SD` firmware path, and the TinyGPSPlus/PlatformIO skeleton, which `firmware/` grows from. I rebuilt the algorithms instead of copying files that would have duplicated `src/lib/gnss`.

## 2. GNSS coordinate conversion

`LocalFrame(origin)` uses an equirectangular tangent plane. It is scaled with the WGS84 radii of curvature at the origin latitude:

- north: metres per degree = M·π/180, where M = a(1−e²)/(1−e² sin²φ)^1.5
- east: metres per degree = N·cosφ·π/180, where N = a/√(1−e² sin²φ)

The scale factors are computed once, so each fix costs two subtractions and two multiplies. The test suite compares distances against an independent Vincenty WGS84 inverse and requires agreement within 5 cm over 3 km. The spherical haversine is about 0.5 % off at 9° N, so it is not used as the reference. The antimeridian is handled.

## 3. Map matching

The `Centerline` is a closed polyline in the direction of travel. The closing segment is implicit, and a repeated last point is tolerated. Each vertex stores its position, unit tangent, segment length and cumulative distance in flat `Float64Array`s, the same layout as the C arrays.

For each fix, `MapMatcher.match(x, y, predictedS?)` does the following:

1. Centres a ±16-segment window on the segment of the dead-reckoned distance `s_prev + v·Δt` when Doppler speed is available, or on the last matched segment otherwise.
2. Projects onto every window segment and keeps the nearest. The window indexes modulo n, so it spans the start/finish seam naturally.
3. If there is no history, or the windowed nearest is more than 30 m away, it falls back to a full scan. A wild full-scan answer is not committed to the history, so one bad fix cannot drag the window to the wrong part of the circuit.

The output is `s ∈ [0, L)` and a signed cross-track error, positive to the left of the direction of travel. `Centerline.delta(a, b)` gives the signed shortest along-track difference in (−L/2, L/2]. Every comparison near the seam goes through it, so 2 m past the line and 3 m before it are 5 m apart, not L − 5.

The tests cover:

- clamped and degenerate projections
- cross-track sign
- seam wraparound in the window (no full scan)
- the window keeping a narrow loop on the correct leg when the other leg is nearer
- fallback after a 700 m jump
- predicted re-centering
- `s` strictly forward and continuous through the seam at 0 noise (max step < 8 m per 10 Hz fix)

Fixes more than 25 m off the centerline are discarded before the gate stage.

## 4. Geographic gate detection

A gate is a timing line with surveyed `left`/`right` endpoints, as seen by a driver going the right way. The valid crossing direction is `forward = rot90CCW(right − left)`.

`compileTrack` does the following:

- finds where each gate crosses the centerline (`gate.s`)
- rejects gates that miss the centerline, that point against the direction of travel, or that are out of driving order
- requires gate 0 to be start/finish

Detection uses the map-matched distance `s`. Lateral noise therefore cannot create or destroy a crossing; only along-track noise matters. Each gate has its own state machine:

```
IDLE ─fix within 60 m before─▶ APPROACH ─fix past the line─▶ PENDING ─K fixes later─▶ accept → DISARMED
  ▲                                                                └─ reject ─▶ IDLE
  └──────────── car > 80 m from the gate (re-arm / hysteresis) ◀──────────────────────────── DISARMED
```

When a crossing is confirmed, the detector refines it from the fixes on both sides of the line:

- **Adaptive window.** The along-track noise is estimated from second differences of `s`. The window is K = 10 fixes per side when σ ≤ 2.5 m and grows in proportion to σ up to 30 per side. Short windows have less model bias; long windows average more noise. The crossing is therefore confirmed 1–3 s after the car passes the line.
- **Doppler mode** (speed reported, as on the BN-880). Speed is projected onto the centerline tangent using course over ground, and integrated into a path-distance curve D(t). Then `s_i ≈ c + α·D_i` is fitted, with α absorbing the path-length vs centerline-length ratio, and solved for `s = gate.s` on the speed-integrated curve. This is exact under acceleration and averages position noise over 2K fixes.
- **Position-only mode.** A quadratic least-squares fit of `s(t)`; the quadratic term absorbs acceleration.

Each guard runs on the whole window, so one noisy fix cannot fake or veto a crossing:

| Guard | Default | Rejection reason |
| --- | --- | --- |
| GNSS quality (before matching) | sats ≥ 6, HDOP ≤ 2.5, fix ≥ 2D, finite, strictly increasing GNSS time | counted in `stats.rejected` |
| Cross-track | ≤ 25 m from centerline per fix | `cross_track` |
| Data gap at the line | ≤ 1.0 s between the straddling fixes | `gap` |
| Minimum speed | ≥ 4 m/s mean over the window | `slow` |
| Minimum movement | ≥ 2 m displacement across the window | `no_movement` |
| Direction | course (or displacement) within 60° of gate forward | `wrong_direction` |
| Inside the gate | mean lateral offset ≤ half-width + 5 m | `outside_gate` |
| Cooldown | ≥ 5 s since the last accepted crossing of that gate | `cooldown` |
| Hysteresis | re-arm only after > 80 m away along track | (state) |

Driving the wrong way never triggers, because `s` goes from past-the-line to before it, which is not the APPROACH → past transition.

Oscillation and jitter at the line cannot double-count, because the gate stays PENDING, then DISARMED, until the car is 80 m clear.

## 5. Lap state machine

`GpsLapEngine` consumes accepted crossings sorted by refined time:

- **Before the first S/F crossing** (`out_lap`): no lap is open. Sector crossings are reported as `ignored_before_start`.
- **First S/F crossing**: opens lap 1 (`lap_start`). This is the flying-lap start.
- **Sector gate k**: accepted only when k is the expected next gate. It records `split = t − lastGateT`. Out-of-order or repeated gates emit `rejected_order` and change nothing.
- **Next S/F crossing**: closes the lap and records:
  - lap time
  - per-sector splits; `null` where a gate was missed
  - max speed (Doppler, or 1 s position-derived without Doppler)
  - `valid`
  
  It then opens the next lap. Laps shorter than 10 s are rejected (`rejected_short_lap`).
- **Validity**: a lap is valid only if every sector gate was seen in order, and sector 1 was not crossed while the engine was waiting for S/F. That second case means the S/F crossing was missed and two laps merged. Only valid laps can become the best lap.
- `live(t)` exposes:
  - phase, lap number, lap/sector elapsed, current splits
  - previous lap, best lap, previous − best, sector deltas vs best
  - live delta vs the best lap at the same lap distance, from a 5 m-bin time-vs-distance trace

While a crossing is pending, fixes are held back and then assigned to the correct lap once the crossing time is known, so max speed and the delta trace are not smeared across laps.

## 6. Timestamp model

Every time in the pipeline is the GNSS fix timestamp (`GnssFix.t`, in seconds). No `Date.now()`, `performance.now()` or frame `dt` enters the GNSS code. A test shifts the time base by 500 000 s and gets identical lap times. On hardware, `t` is the receiver's UTC time-of-fix (hh:mm:ss.cc), with midnight rollover handled, not `millis()`.

## 7. Browser cockpit

`SessionEngine.timing` selects the source:

- **`"gps"` (default)**: the car moves along the existing speed profile. Every 0.1 s of simulated time it emits a noisy fix with σ = 1.4 m, Doppler speed and true course over ground, stamped with simulated GNSS time. Laps, sectors, best and last come only from `GpsLapEngine`.
- **`"synthetic"`**: the original distance-wrap lap logic, unchanged, for UI work. Open the app with `?timing=synthetic`, or call `useSession.getState().setTiming("synthetic")`.

Both sources fill the same `SessionEngine` fields, and the store's snapshot is built the same way, so the React screens do not know which source is active. All six screens (Dash, Map, IMU, Laps, Log, Build) and CSV export are kept. The only UI change: a sector that was not seen in order shows `—` on the Laps screen, and an empty field in the CSV.

In GPS mode the predictive delta is blanked for the 1–3 s between the car passing the line and the crossing being confirmed. Pause stops fixes and GNSS time together; resume carries on with identical lap times (tested).

Browser check: headless Chromium against `vite dev`, 2 minutes per mode. GPS mode closed 2 laps; synthetic mode closed 1 lap. There were no page errors. One console error (`net::ERR_BLOCKED_BY_RESPONSE.NotSameOrigin`, a cross-origin asset) is unrelated to timing.

## 8. Firmware (ESP32-S3 + BN-880)

**`firmware/lib/apex_timing/apex_timing.h`** (C++17, header-only, no heap, no STL containers):

- the whole pipeline: `Track::compile`, `MapMatcher`, `GateDetector`, `LapEngine`
- fixed limits: 1536 centerline points (override with `-DAPEX_MAX_CENTER_PTS`), 16 gates, a 128-fix ring, a 64-fix refinement window, 64 recent laps in RAM
- `sizeof(Track)` = 75 KB, `sizeof(LapEngine)` = 48 KB, both static

**Parity**: `npm run firmware:test` exports three scenarios from the TypeScript engine and replays them through the C++ code with `g++ -Wall -Wextra -Werror`:

- club, 3 m, Doppler
- street, 1.5 m, position-only
- fast, 10 m, 5 % bad and 2 % dropped fixes

Result: same lap count, validity and splits, max |C++ − TS| = 0 s on every lap.

**`firmware/src/main.cpp`** (Arduino):

- configures the BN-880 over UBX: 115200 baud, 10 Hz measurement rate, GGA + RMC only so 10 Hz fits the UART
- parses NMEA with TinyGPSPlus and builds `GnssFix` from the time-of-fix, position, speed, course, sats and HDOP
- runs the engine and prints `FIX,…` and `EVT,LAP_START|SECTOR|LAP|REJECT_*` lines over USB serial
- loads the track definition over serial (same text format as the host fixtures, terminated by `END`)

GNSS parsing stays in `main.cpp`; the timing core never sees NMEA.

**Build**: `pio run` for `esp32-s3-devkitc-1` succeeds. RAM 50.9 % (166 868 / 327 680 B), Flash 9.7 %.

**Not implemented yet:**

- the 3.5" display driver
- microSD logging and track loading from SD (fixes are printed in a replayable format instead)
- UBX `NAV-PVT` parsing (it would give fix type and speed accuracy directly)
- on-target timing measurements
- tests on real hardware

## 9. Validation methodology

`npm run validate:gps` runs 18 main scenarios (3 synthetic tracks × 6 noise levels) at 1000 laps each, plus 9 supplementary ones (position-only receiver, and a degraded stream). That is 27 000 simulated laps, at 10 Hz with seed 2026.

**Truth**:

- the car follows the centerline with a smooth lateral offset of up to ±2.5 m (different every lap) and smooth pace variation
- speed follows corner curvature with 6 m/s² acceleration and 11 m/s² braking limits
- the truth crossing time is the moment the offset path crosses the physical gate line, interpolated within a 5 ms step

**Measurement**:

- white Gaussian east/north noise with σ = noise level per axis
- Doppler speed noise 0.1 m/s, course noise 0.5°
- 10–16 satellites, HDOP 0.6–1.2

**Scoring**: detected crossings are matched to truth within 1 s. A lap counts only if both of its crossings match consecutive truth crossings. Pass/fail (the exit code) requires, for every main scenario:

- 0 missed laps and sectors at ≤ 5 m (≤ 0.1 % missed laps at 10 m)
- 0 duplicate laps or sectors
- P95 lap error ≤ 10 / 25 / 60 / 120 / 200 / 400 ms at 0 / 0.5 / 1.5 / 3 / 5 / 10 m

The racing-fitness band is separate:

- **GREEN**: 0 detection errors, P95 ≤ 50 ms and max ≤ 100 ms
- **YELLOW**: 0 detection errors and P95 ≤ 150 ms
- **RED**: any detection error, or P95 > 150 ms

The thresholds were written after development runs on seed 1. The report run uses an independent seed and the unit tests use another (11).

Two simulator artifacts were found and fixed during development. Both made the algorithm look worse, not better:

- an unbounded speed profile (12 m/s jumps in 0.1 s)
- kinked offset paths at centerline vertices, which spiked the truth velocity

It is ≈ 1.96 σ at every level, which is the injected lateral noise itself: map matching cannot remove lateral noise, and it does not need to, because detection uses `s`. A matching failure would show up as a residual far above that, as along-track error or as full scans. None appeared; the counters are in the report.

| Band | Noise σ per axis | Behaviour |
| --- | --- | --- |
| GREEN | ≤ 1.5 m | Exact detection; P95 ≤ 36 ms, max ≤ 84 ms on every track |

Timing first leaves GREEN at **3 m σ**. The error scales almost linearly with σ and inversely with speed at the line; the slow street S/F is the worst case. Detection did not degrade at any tested level.

The supplementary runs are informational:

- **Position-only receiver**: costs about 1.5× timing accuracy (club P95 48 ms at 1.5 m, 88 ms at 3 m), and its max-speed estimate is poor at ≥ 1.5 m.
- **3 m with 5 % bad and 2 % dropped fixes**: 0 detection errors, with timing close to clean 3 m.

**What this means for the BN-880.** u-blox specifies the M8N at about 2.5 m CEP in open sky. That is roughly σ ≈ 2.1 m per axis, which falls on the GREEN/YELLOW boundary. Real errors are time-correlated and partly cancel within a lap, so the hardware may do better than this white-noise model suggests, or worse under multipath. Only a real track test can settle it.

## 11. Known limitations

- The synthetic tracks are not surveyed circuits. Real centerlines and gates must come from surveyed or logged coordinates, through `GeoTrackDef`.
- The noise model is white. There is no correlated bias, multipath bursts, receiver latency, or antenna shadowing (the degraded-stream run covers dropouts and bad-quality fixes only).
- A single-gate track (S/F only) cannot tell a missed S/F crossing from a slow lap. Use at least one sector gate.
- Laps confirm 1–3 s after the line; the dash shows the new lap after that delay.
- Pit lanes are not modelled. A pit lane closer than half-width + 5 m to the S/F line would need its own gate geometry.
- Max-speed accuracy depends on Doppler speed; without it, it is poor at ≥ 1.5 m.
- `npm test` in this repo already fails in 15 template scaffold tests under `scripts/`, which are identical on `main`. Because `npm test` chains with `&&`, run `npm run test:timer` directly for the timing suite.

## 12. Next hardware step

1. **Wire it up.** BN-880 TX → ESP32-S3 GPIO18, RX ← GPIO17, VCC 5 V (or 3.3 V per board), GND. The compass I²C pins can be left unconnected. Put the antenna flat with a clear sky view.
2. **Flash.** In `firmware/`, run `pio run -t upload`, then `pio device monitor`. Expect `GNSS_READY`. Then confirm the `FIX,` lines arrive 10 per second with sats ≥ 8 and HDOP < 1.5. If they arrive at 1 Hz, the UBX config did not take; check the baud rate first.
3. **Static test** (car parked for 10 minutes). Log `FIX` lines and compute the scatter, which gives your real σ. Feed it back into `npm run validate:gps` to see which band you are actually in. The car must not register any laps.
4. **Survey the circuit.** Drive 2–3 slow laps logging fixes, average them into a centerline (3–4 m spacing), and put gates across straights with surveyed left/right points. Export in the `.track` text format and send it over serial.
5. **First track test.** Run 10+ laps alongside a reference (transponder, light beam, or a known-good timer). Compare lap by lap: no missed or duplicate laps, and timing differences against the band above.
6. **Then build the rest of V1**: the display, SD logging (the `FIX` lines are already in replayable form), and UBX `NAV-PVT`.
